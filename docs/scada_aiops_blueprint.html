이 프로그램은 운영자용 로컬 웹 대시보드다. 서버 장비가 토해내는 로그 파일을 주기적으로 스캔해 상태 변화를 감지하고, 변화가 생기면 내장된 로컬 AI API에 물어 장애/전조/정상 여부와 권장 조치를 받아온다. 동시에 SSH로 운영 서버군에 접속해 프로세스 상태를 점검하고, 문제가 있으면 승인 기반으로 복구 명령을 실행한다. 대시보드(8000번 포트)와 AI API(8001번 포트)가 같은 EXE 안에서 함께 뜨기 때문에 외부 AI 서버 주소를 입력할 필요가 없다.

이 문서의 쓰임새

사람이 읽고 이해하는 것과, 이 문서를 그대로 Claude 같은 코딩 에이전트에게 주고 "이 사양대로 프로젝트를 만들어줘"라고 시켰을 때 동일한 결과물이 나오는 것, 두 가지를 동시에 노리고 작성했다. 그래서 일반적인 설명보다 정규식·명령어· 테이블 스키마 같은 1차 자료를 훨씬 많이 그대로 인용한다.

01배경과 목적

프로젝트에 포함된 샘플 로그(psrt/*.txt)를 보면 djd1ap01, djd1ap02 같은 호스트명과 rtccntl, SQCNTL, XCOM, dbcXXX, goccui 같은 프로세스 이름이 등장한다. 이는 전형적인 전력계통 EMS(Energy Management System) / SCADA 백엔드의 프로세스 구성이며, AP(Application/Application Processor)와 FE(Front-End) 이중화 서버 구조, getconfig2· psrt·ungoxa 같은 벤더 전용 운영 명령어를 사용하는 운영 환경을 대상으로 한다. 즉 이 도구는 급전소/운영센터의 SCADA/EMS 서버 인프라를 감시·복구하는 현장 운영 보조 도구로 설계됐다.

tools/ 폴더에는 이 프로그램의 소개 보고서, 운영자 매뉴얼, 보안성 검토서, 발표용 PPT를 자동 생성하는 스크립트(python-docx, python-pptx, Pillow 기반)가 들어 있는데, 여기 하드코딩된 문구가 프로젝트의 의도를 가장 명확하게 요약한다:

핵심 메시지 (tools/build_introduction_manual_docs.py)

"본 프로그램은 운영자가 기존 접근 권한 범위 안에서 로그 분석, 상태 점검, 장애 복구 판단을 빠르게 수행하도록 돕는 로컬 통합 도구입니다. 대시보드와 AI API가 동일 PC에서 함께 구동되므로 외부 AI 서버 주소 입력 및 불필요한 네트워크 노출을 줄였습니다."

정리하면 목적은 세 가지다. ① 서버 하드웨어/로그 상태 확인을 표준화하고, ② 장애 징후를 AI로 조기에 잡아내며, ③ 복구는 자동 실행이 아니라 운영자 승인 기반으로 안전하게 수행하는 것.

02전체 아키텍처

단일 PyInstaller onefile EXE 안에 두 개의 FastAPI 프로세스가 뜬다. 메인 프로세스가 대시보드(8000)이고, 그 안에서 LocalAIServer가 로컬 전용 AI 진단 API(8001)를 사이드카로 기동한다. 운영자는 브라우저로 8000번만 접속하며, 8001번은 루프백에서만 열린다.

05부팅 시퀀스

launcher.py가 PyInstaller onefile의 진입점이다. 백그라운드 스레드로 /health를 폴링하다가 서버가 뜨면 기본 브라우저를 자동으로 연다 (SCADA_NO_BROWSER=1이면 생략). 그 뒤 uvicorn.run(app, host='127.0.0.1', port=8000)으로 메인 앱을 구동한다.

실제 초기화는 app/main.py의 lifespan 컨텍스트에서 순서대로 일어난다.

AI API URL 강제 고정

db.set_setting('ai_api_url', INTERNAL_AI_API_URL) — 사용자가 예전에 외부 주소를 저장해뒀어도 매 기동 시 로컬 8001로 되돌린다.

로컬 AI 사이드카 기동

local_ai_server.start()를 스레드풀에서 실행. ai_bundle/api_server.exe가 있으면 그 프로세스를 서브프로세스로 띄우고, 없으면(또는 SCADA_AI_USE_INTERNAL=1이면) 같은 프로세스 안에서 uvicorn.Server를 별도 스레드로 구동한다.

로그 스캐너 시작

DB에 저장된 scan_interval(기본 60초)로 ScannerService.start() 백그라운드 루프 시작.

헬스체크 자동 루프 (선택)

health_check_enabled 설정이 켜져 있으면 health_check_interval(기본 300초) 간격으로 HealthCheckService.start_auto() 시작.

종료 시 정리

lifespan의 finally 블록에서 스캐너 → 헬스체커 → AI 사이드카 순으로 정지시킨다.

06인증 시스템

별도 인증 라이브러리 없이 표준 라이브러리만으로 구현한 최소 세션 인증이다. 관리자 계정이 하나도 없으면(admin_password_hash 미설정) 모든 요청이 /setup으로 강제 리다이렉트된다.

항목방식
비밀번호 해시pbkdf2_hmac('sha256', ..., iterations=260_000), salt 16바이트 hex. 저장 형식: pbkdf2_sha256$260000$salt$base64digest
세션 토큰username|expires_at를 HMAC-SHA256으로 서명 후 base64url. 시크릿은 최초 기동 시 secrets.token_urlsafe(48)로 생성해 DB에 저장
쿠키scada_aiops_session, httponly, samesite=strict, 만료 12시간. SCADA_AUTH_COOKIE_SECURE로 secure 플래그 제어
미들웨어 게이트@app.middleware('http')에서 공개 경로(/health, /login, /setup, /static/*) 외 모든 요청에 세션 검사. API 요청은 401/403 JSON, 페이지 요청은 302 리다이렉트로 분기
오픈 리다이렉트 방지_safe_next_path()가 next 파라미터를 검증 — // 시작, 백슬래시, 제어문자가 있으면 /로 무시

07데이터베이스 스키마

단일 SQLite 파일(data/scada_dashboard.db)에 12개 테이블이 있다. Database._init_db()가 매 기동 시 CREATE TABLE IF NOT EXISTS를 실행하므로 별도 마이그레이션 도구 없이도 스키마가 항상 최신 상태로 맞춰진다. 시간대는 최초 1회 tz_migration_done 플래그로 UTC→KST(+9h) 이관을 수행한 뒤 이후 모든 신규 레코드는 datetime('now','localtime')로 기록한다.

① Primary 서버 탐색 & FAILED 노드 복구 — recover_group()

② Warm Start — 전체 AP 장애 시나리오

check_warm_start_required()는 등록된 모든 AP의 getconfig2를 확인해, 모든 AP가 FAILED거나 모든 AP의 getconfig2 응답 형식이 깨져있으면 Warm Start 대상으로 판정한다. 단, SSH 자체가 전부 안 되면(all_aps_unreachable) 이는 네트워크/감시망 문제일 수 있어 Warm Start 대상에서 제외한다 — SSH가 안 되면 Warm Start 명령도 어차피 실행할 수 없기 때문.

운영자 승인 필수

Warm Start는 POST /api/recovery/warm-start/{group}로 운영자가 명시적으로 눌러야만 실행된다. 백엔드는 실행 직전 check_warm_start_required를 재검증해, 필요 상태가 아니면 409로 거부한다 — 자동 실행을 원천 차단한 설계.

실행 시 AP01을 최우선 후보로, 나머지 AP는 이름순으로 순회하며 각 서버의 홈 디렉터리에서 ./start_warm.sh 존재/읽기 가능 여부를 확인한 뒤 백그라운드로 실행하고 PID를 마커 문자열로 회수한다. 실제 실행 셸 명령은 방어적으로 짜여 있다 — 스크립트가 없거나 읽기 권한이 없으면 각각 다른 에러 마커를 내보내 다음 AP로 폴백할 수 있게 한다.

bash (SSH invoke_shell로 전송)Warm Start 실행 명령
cd ~ && \
if [ ! -f ./start_warm.sh ]; then echo "__WARM_ERROR__: missing ./start_warm.sh"; \
elif [ ! -r ./start_warm.sh ]; then echo "__WARM_ERROR__: unreadable ./start_warm.sh"; \
else nohup sh ./start_warm.sh > /tmp/start_warm.log 2>&1 & echo "__WARM_STARTED__:$!"; fi

출력에서 __WARM_STARTED__:<PID> 마커가 잡히면 성공, __WARM_ERROR__: 마커가 잡히면 다음 AP 후보로 넘어간다. nohup ... &로 스크립트 자체는 백그라운드에 남겨두고 SSH 세션은 즉시 빠져나온다 — 웜스타트 자체는 오래 걸릴 수 있기 때문.

③ RTC / SQ / PSRT 프로세스 복구 — Primary AP(AP.1.P) 대상

getconfig2 출력에서 ONLINE ... AP.1.P 패턴을 만족하는 호스트를 "메인 처리 서버(Primary AP)"로 식별한 뒤, 그 서버에서만 3종 프로세스를 점검·복구한다. 상태 파싱은 모두 psrt 출력(NAME : COPY : STATE : EC : PID : QID : MSGS PDS : MSGS IPC 콜론 구분 표)을 기반으로 한다 — 실제 psrt/*.txt 샘플이 이 포맷 그대로다. STATE 컬럼 값으로는 ACTIVE/DELAY/INFMSGWAIT/MSGWAIT 등이 관측된다(정상 판정 로직은 상태값 자체가 아니라 "해당 이름의 프로세스가 목록에 존재하는지"만 본다).

구분상태 확인정상 판정 기준복구 명령재확인 대기
RTCpsrt rtc이름이 rtc로 시작하는 프로세스가 1개 이상rtcx -s (10초 대기) → rtcx -c (15초 대기)즉시 재조회
SQ (사활해석)psrt SQSQCNTL과 SQSCHD 둘 다 존재sqdown (5초) → squp (10초)즉시 재조회
PSRT 핵심 프로세스psrt (전체)감시 대상 이름이 모두 목록에 존재 (기본 fdevtd, fsmon, 그룹별 설정 가능)누락된 각 프로세스에 istop {name} (3초) → istart {name}10초(PSRT_VERIFY_DELAY)

PSRT 감시 대상은 app_settings의 psrt_processes:{group_name} 키에 JSON으로 저장되며, PUT /api/recovery/psrt-processes/{group}로 운영자가 이름·중지명령·시작명령을 자유롭게 커스터마이즈할 수 있다(기본값은 fdevtd/fsmon, 각각 istop/istart).

HealthCheckService는 그룹별 asyncio.Lock으로 중복 실행을 막는다 — 이미 점검 중인 그룹에 새 요청이 오면 진행 중 응답을 그대로 돌려주고 새로 시작하지 않는다. 그룹 점검 로직(_check_group_impl)의 판정 우선순위는 세 단계다.

정상 응답 확보

그 출력으로 클러스터 전체 노드 상태를 파싱해 각 서버에 반영, AP.1.P를 찾아 RTC/SQ/PSRT까지 연쇄 점검.

AP.1.P가 이전 점검과 다른 서버로 바뀌었을 때(페일오버 발생), 이전 Primary에 남아있던 RTC/SQ 상태 레코드는 clear_other_rtc_statuses_in_group() / clear_other_sq_statuses_in_group()로 정리해 stale 데이터가 화면에 남지 않게 한다. RTC·SQ·PSRT 중 비정상이 감지되면 헬스체크 루프 자체가 그 자리에서 즉시 자동 복구를 실행하고 결과를 recovery_history에 event_type='auto_recovery'로 남긴다 — 이 세 프로세스만큼은 사람 승인 없이 자동 복구되는 유일한 경로다(반대로 노드 자체 복구와 Warm Start는 항상 수동 승인).

13실시간 갱신 (SSE)

WebSocket 대신 Server-Sent Events 3종으로 모든 실시간성을 처리한다 — 방향이 서버→클라이언트 단방향뿐이라 SSE가 더 단순하다는 판단으로 보인다. 다만 백엔드가 SSE 엔드포인트를 갖고 있다는 것과, 프론트가 실제로 그걸 EventSource로 구독한다는 것은 별개다 — 아래 표의 "프론트 실제 구현" 열을 보면 3채널 중 진짜 서버 푸시를 받는 건 하나뿐이다.

채널트리거백엔드 의도프론트 실제 구현
/api/stream스캐너가 새 이벤트를 만들면 asyncio.Event.set()/clear()대시보드 자동 갱신용 SSEconnectSSE() — 이름과 달리 진짜 SSE를 구독하지 않는다. setInterval(loadDashboard, 30000)로 30초 폴링만 한다.
/api/recovery/recover/{group}복구 스레드가 queue.Queue에 진행 로그 push, call_soon_threadsafe로 이벤트루프에 브리지복구 진행 콘솔 실시간 로그recoverGroup() — 3채널 중 유일하게 진짜 EventSource를 생성해 onmessage로 step/success/warn/error/info/done 타입 메시지를 파싱한다.
/api/recovery/eventsRTC/SQ/PSRT 자동복구 또는 수동복구 완료 시 _broadcast_recovery()가 구독자 큐 전원에 push복구완료 모달 실시간 알림connectRecoveryEventsSSE() — 역시 이름과 달리 실제로는 catchUpMissedRecoveries()를 10초 간격으로 폴링한다. localStorage의 recovery_last_seen_id로 마지막으로 본 이력을 기억해, 새로고침 후에도 놓친 복구를 따라잡는다.
재현 시 주의

이 표만 보고 "3채널 모두 EventSource로 구현하면 되겠다"고 재현하면 원본과 동작이 달라진다. 실제로 프론트가 서버 푸시를 소비하는 채널은 /api/recovery/recover/{group} 하나뿐이고, 나머지 둘은 백엔드에 SSE 엔드포인트가 버젓이 존재함에도 프론트가 단순 폴링으로 대체해 쓰고 있다 — 아마 초기엔 셋 다 SSE로 설계했다가 프론트 구현 단계에서 두 곳은 더 단순한 폴링으로 바뀌었고, 함수명(connect...SSE)은 리팩터링되지 않은 채 남은 것으로 보인다.

대시보드 라우트 + 인증

6장 인증 방식(pbkdf2 + HMAC 세션 쿠키)과 12장 API 표를 그대로 구현.

SSH 복구 서비스

10장의 명령 시퀀스·정규식·대기시간 표를 그대로 옮긴다. 실제 대상 서버가 없다면 _ssh_exec를 모킹해서 나머지 로직(파싱/판정/DB 반영)부터 검증.

헬스체크 자동화

11장의 그룹 락 + 3단계 판정 + RTC/SQ/PSRT 연쇄 자동복구.

프론트엔드

템플릿 7종 + app.js. 13장 SSE 3채널부터 붙이면 나머지 렌더 함수들이 자연히 뒤따른다.

패키징

15장 스펙대로 PyInstaller onefile 빌드, launcher.py의 브라우저 자동 오픈 포함.

가장 재현하기 어려운 부분

AI 모델(XGBoost 가중치, action_db.pkl의 실제 사례 벡터)은 실제 라벨링된 학습 데이터 없이는 값 자체를 복제할 수 없다. 대신 계약(인터페이스)은 100% 복제 가능하다 — 402차원 피처 구성, threshold 0.05, 코사인 유사도 0.65 게이트만 지키면 같은 형태로 동작하는 대체 모델을 끼워 넣을 수 있다.

SCADA AIOps Dashboard 소스 코드 전체(약 5,300줄: app/ 3,900줄 + tools/ 1,400줄)를 직접 정독하여 작성한 재현용 기술 문서.
