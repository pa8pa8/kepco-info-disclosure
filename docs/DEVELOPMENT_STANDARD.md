# 개발 표준 (정보공개 청구 지원 시스템)

## 1. 목적
이 문서는 프로젝트의 변경 이력을 명확히 남기고, 협업과 유지보수를 표준화하기 위한 기준을 정의한다.

모든 변경은 다음 원칙을 따라야 한다.

- 무엇을 왜 변경했는지 기록한다.
- 변경 결과를 검증하고 문서화한다.
- 10년 전 도입된 서버와 콘솔 PC에서도 최소한의 의존성으로 동작해야 한다.
- GitHub 업로드는 별도 저장소 초기화 및 push 단계가 있어야 하며, 코드 수정 자체가 자동 업로드되는 것은 아니다.

---

## 2. 변경 로그 원칙

### 2.1 변경 기록은 필수
모든 코드 수정, 설정 변경, 환경 수정, 데이터 구조 변경, 문서 수정에 대해 다음 정보를 남긴다.

- 변경 일시
- 작성자
- 작업 항목/이슈 번호
- 변경 요약
- 변경 상세
- 검증 방법
- 위험도
- 이후 조치

### 2.2 파일 위치
모든 변경 로그는 다음 경로에 남긴다.

- `logs/changes/YYYY-MM-DD/`

파일 이름은 다음 형식으로 작성한다.

- `ISSUE-0001-short-description.md`

예:

- `logs/changes/2026-09-06/FOIA-0001-login-role-check.md`

### 2.3 로그 템플릿
각 로그 파일에는 아래 구조를 사용한다.

```md
# 변경 기록

- 일시: 2026-09-06 10:30
- 작성자: 사용자명
- 작업번호: FOIA-0001
- 변경 유형: feature | fix | docs | config | refactor | test
- 상태: draft | reviewed | approved | deployed

## 변경 요약
간단한 설명

## 변경 내용
- 항목 1
- 항목 2

## 원인
왜 이 변경이 필요한가

## 검증
- 확인 방법
- 결과

## 리스크
- 가능성
- 영향 범위

## 다음 조치
- 후속 작업
```

## 3. 자동화 원칙

### 3.1 로그 자동 생성
개발자는 수동으로 매번 문서를 작성하는 대신, 로컬 스크립트를 사용해 표준 포맷으로 로그를 생성한다.

사용 도구:

- `python tools/log_change.py --ticket FOIA-0001 --summary "로그인 권한 체크 수정" --type fix`

스크립트는 다음을 자동으로 수행한다.

- 현재 날짜 디렉터리 생성
- 표준 파일명 생성
- 기본 템플릿 채우기
- 변경 기록 파일 작성

### 3.2 커밋 메시지 표준
모든 Git 커밋 메시지는 다음 형식을 따른다.

```text
[TYPE] short summary

- details
- validation
```

예:

```text
[fix] login role check

- restrict staff access to their own assignment
- validate login redirect flow
```

권장 타입:

- `feat`: 기능 추가
- `fix`: 버그 수정
- `docs`: 문서 작업
- `refactor`: 구조 개선
- `config`: 설정 변경
- `test`: 테스트 추가/수정

### 3.3 GitHub 자동 업로드 여부
이 표준은 GitHub 업로드를 자동으로 수행하지 않는다. GitHub 반영은 별도의 명령으로 수행한다.

필수 절차:

```bash
git add .
git commit -m "[fix] summary"
git push origin main
```

이 프로젝트 현재 워크스페이스는 Git 저장소가 초기화되어 있지 않으므로, GitHub 업로드를 자동으로 수행할 수 있는 상태가 아니다.

## 4. 개발 절차 표준

### 4.1 작업 흐름
1. 작업 항목을 식별한다.
2. 로그 파일을 생성한다.
3. 변경을 최소 단위로 나눈다.
4. 코드/설정/문서를 수정한다.
5. 검증을 수행한다.
6. 로그에 검증 결과를 기록한다.
7. 커밋 메시지와 변경 로그를 일치시킨다.
8. 필요 시 원격 저장소에 push 한다.

### 4.2 브랜치 전략
권장 브랜치 명명 규칙:

- `feature/FOIA-0001-login-role-check`
- `fix/FOIA-0002-watch-scan-bug`
- `docs/FOIA-0003-standard-update`

### 4.3 병합 기준
- 최소 1회 리뷰
- 변경 로그 파일 작성
- 검증 명령 결과 기록
- 문서와 코드가 일치해야 함

## 5. 호환성 기준 (10년 전 서버/콘솔 PC 대응)

### 5.1 기술 기준
다음 조건을 만족해야 한다.

- Python 3.8 이상 사용
- 외부 패키지 최소화
- 최신 OS 전용 기능 사용 금지
- Windows PowerShell/기본 cmd 환경에서 동작 가능
- Linux/Unix 서버에서도 최신 셸 의존성 없이 동작 가능

### 5.2 권장 규칙
- `subprocess` 호출은 단순 명령 기반으로 유지
- `pathlib` 사용 권장
- PyInstaller/onefile 빌드용 구조 유지
- 외부 런타임 라이브러리 의존 최소화
- 로컬 파일 기반 설정 사용

### 5.3 금지 사항
- Docker 전용 설정만 사용
- 최신 Python 3.12 전용 문법 의존
- 최신 Linux 전용 shell 스크립트
- 외부 서비스 의존성이 높은 설치 절차
- 브라우저 전용 기능을 필수 로직으로 고정

## 6. 문서화 표준

### 6.1 문서 관리
- 기능 설명은 README에 최소 요약을 남긴다.
- 자세한 동작 기준은 `docs/` 하위에 정리한다.
- 운영 절차는 `docs/ops/` 또는 `docs/` 하위에 유지한다.

### 6.2 문서 업데이트 조건
다음 경우에는 반드시 문서를 함께 업데이트한다.

- UI 변경
- API 변경
- 역할 권한 변경
- 설정값 추가/삭제
- 배포 방식 변경
- 데이터 구조 변경

---

## 7. 검증 표준
모든 수정 후에는 다음을 수행한다.

1. 기능이 정상 동작하는지 확인
2. 로그 파일이 작성되었는지 확인
3. 변경 내용을 문서에 반영했는지 확인
4. 영향 범위를 점검한다
5. 실패 조건과 보완 계획을 남긴다

검증 명령 예시:

```bash
python -m compileall app tools
python tools/log_change.py --ticket FOIA-0001 --summary "validation example" --type fix
```

---

## 8. 운영 규칙

- 서버와 콘솔 PC 모두에서 제어 가능한 실용적인 구조를 우선한다.
- 복잡한 자동화는 장기 유지보수를 고려해 설계한다.
- 변경 로그는 사람이 읽을 수 있어야 하며, AI 도구가 추적할 수 있어야 한다.
- 실무 기준은 “기록이 남고, 검증이 보이며, 오래된 환경에서도 동작하는 것”이다.

---

## 9. 핵심 원칙 요약
이 프로젝트의 개발 표준 핵심은 다음 5가지다.

1. 변경은 로그로 남긴다.
2. 로그는 자동 생성한다.
3. GitHub 업로드는 별도 단계로 분리한다.
4. 오래된 서버와 콘솔 PC까지 고려해 설계한다.
5. 문서, 코드, 로그, 검증 결과를 모두 같이 유지한다.

이 기준을 따르면 프로젝트가 더 안정적으로 관리되고, 포트폴리오/운영 이력/감사 대응까지 준비할 수 있다.
