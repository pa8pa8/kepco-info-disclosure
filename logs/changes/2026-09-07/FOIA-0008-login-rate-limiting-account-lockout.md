## 변경 내용
- `app/main.py`: `_LOGIN_MAX_ATTEMPTS`(5)/`_LOGIN_LOCKOUT_SECONDS`(300) 상수와 모듈
  전역 `_login_attempts` 딕셔너리 추가. `_login_lockout_remaining()`으로 잠금 잔여
  시간 조회, `_register_login_failure()`로 실패 카운트 증가 및 임계치 도달 시 잠금
  설정, `_register_login_success()`로 로그인 성공 시 카운트 초기화.
- `/login` 라우트: 요청 시작 시 잠금 여부를 먼저 확인해 잠겨 있으면 비밀번호 검증도
  하지 않고 429 + "N초 후 다시 시도해주세요" 메시지로 즉시 응답. 실패 시
  `_register_login_failure`, 성공 시 `_register_login_success` 호출.
- 메모리 기반 구현(단일 uvicorn 워커 전제) — DB 스키마 변경이나 새 의존성 없이
  가장 단순하게 구현. 여러 워커/여러 인스턴스로 확장할 경우 DB나 공유 캐시로
  옮겨야 함을 코드 주석과 점검 문서에 남김.

## 검증
- 확인 방법: 격리 환경(포트 8097, 별도 DB)에서 `manager` 계정으로 잘못된 비밀번호
  5회 연속 시도(각각 401 확인) → 6번째 시도 429 확인 → 잠긴 상태에서 올바른
  비밀번호로도 429인지 확인 → 잠기지 않은 다른 계정(`dispatcher`)은 정상 로그인(303)
  되는지 확인. `python -m compileall app` 통과.
- 결과: 전부 기대대로 동작. 계정별로 독립적으로 카운트됨을 확인.

## 리스크
- 영향 범위: 서버 재시작 시 모든 잠금·실패 카운트가 초기화됨(메모리 기반이므로 의도된
  동작). 정상적인 사용자가 비밀번호를 5번 이상 잘못 입력하면 5분간 로그인이 막히므로,
  실제 배포 시 계정 찾기/비밀번호 재설정 창구(시스템관리자에게 문의 등)를 안내할 필요.
- 주의사항: IP가 아닌 계정 단위로만 잠그므로, 공격자가 여러 계정을 동시에 시도하는
  것은 막지 못함(계정별 잠금이라 개별 계정 보호 목적에는 충분하나 전체 무차별 대입
  자체를 막는 것은 아님).
