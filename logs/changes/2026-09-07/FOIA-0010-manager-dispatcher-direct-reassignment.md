## 변경 요약
총괄관리자/배정담당자가 이미 배정된(미확정) 청구를 담당자 동의 없이 직접 재배정할 수
있는 기능 추가. FOIA-0009(업무담당자 거절)로 해결하지 못했던 "재배정 불가" 공백의
나머지 절반.

## 변경 내용
- `app/db.py`: `reassign_request(request_id, assigned_to, assigned_by, previous_assignee)`
  신규 — `assign_request`와 달리 이전 담당자 → 새 담당자를 `decision_log`에 `A → B` 형식으로
  남긴다(`step_key='reassign'`). 재배정 시에도 `reassign_candidates_json`은 정리.
- `app/main.py`: `POST /api/requests/{id}/assign`에서 "이미 배정된 청구입니다" 409 차단을
  제거하고, 이미 배정돼 있으면 `reassign_request`, 아니면 기존 `assign_request`를 호출하도록
  분기. 동일 담당자로 재배정 시도는 409로 거부. `request_detail`에 `can_reassign`(미확정 +
  배정담당자/총괄관리자 + 이미 배정됨) 계산 추가, 이 경우 `staff_directory`에서 현재
  담당자를 제외.
- `app/templates/request_detail.html`: "담당자 재배정" 패널 신규(현재 담당자 표시 + 검색해서
  클릭하면 즉시 재배정). 배정담당자가 보던 "배정 대기 중입니다" 안내 문구가 이미 배정된
  건에도 잘못 뜨던 것을 "현재 OOO님이 처리 중입니다"로 수정.

## 원인
FOIA-0009 완료 후 사용자에게 다음 작업을 물었고, "총괄관리자/배정담당자의 직접 재배정
기능"을 선택. 직전 역할별 재점검에서 "총괄관리자조차 재배정 불가"로 지목했던 항목의
나머지 절반.

## 검증
- 확인 방법: 격리 환경(포트 8094, 별도 DB)에서 (1) staff1에게 배정 후 판단 1단계 진행 →
  manager가 staff6으로 직접 재배정 → dispatcher가 다시 staff8로 재배정, (2) 동일 담당자로
  재배정 시도 시 409, (3) 이전 담당자(staff1)는 접근 시 303 리다이렉트, (4) 새 담당자
  (staff6)는 접근 가능하고 판단 진행 상태(1단계 완료, 다음 단계 정보부존재)가 그대로
  유지되는지, (5) 처리 이력에 `담당자 재배정 staff1 → staff6`(manager),
  `staff6 → staff8`(dispatcher) 로그가 정확히 남는지, (6) 이미 완료(진정질의로 확정)된
  청구는 재배정 시도 시 409로 거부되는지 전부 curl로 확인. Playwright로 관리자 화면에서
  패널이 실제로 잘 보이고 현재 담당자가 검색 후보에서 제외되는지 스크린샷 확인.
- 결과: 전부 기대대로 동작. `python -m compileall app` 통과.

## 리스크
- 영향 범위: 기존 "최초 배정"(`assign_request`) 경로는 그대로 유지, 이미 배정된 경우에만
  새 분기(`reassign_request`)를 탄다 — 회귀 없음.
- 주의사항: 재배정에 담당자 동의나 알림이 없다 — 업무담당자는 본인이 처리 중이던 청구가
  갑자기 목록에서 사라져도 별도 통보를 받지 못한다(FOIA-0009/이번 건 모두 공통, 실시간
  알림 기능 자체가 아직 없음 — `docs/PROJECT_REVIEW_2026-09-07.md` 6절 "새로 배정돼도
  알림이 없음" 항목과 동일한 근본 원인).
