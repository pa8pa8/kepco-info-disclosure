## 변경 요약
배정담당자에게 `/requests` 전체 목록/검색 대신, 청구인 이름이 정확히 일치하는 과거
청구만 조회할 수 있는 `/requester-history` 신규 추가. 역할별 재점검 마지막 항목 해결.

## 변경 내용
- `app/db.py`: `find_requests_by_requester_name(name, exclude_id=None, limit=50)` 신규 —
  `list_requests`의 `q` 검색(원문·요청대상까지 훑는 LIKE 검색)과 달리 `requester_name`
  **정확 일치**만 조회. 전체 열람으로 악용되지 않도록 의도적으로 좁게 설계.
- `app/main.py`: `GET /requester-history` 신규(배정담당자·총괄관리자). 쿼리파라미터
  `name`이 비어 있으면 검색폼만 보여주고 결과는 아무것도 반환하지 않음.
- `app/templates/requester_history.html` 신규, `base.html` 배정담당자 네비게이션에
  "청구인 이력 조회" 링크 추가.
- `app/templates/dispatch.html`: 각 미배정 카드에 "이 청구인 이력 보기 →" 바로가기
  (해당 카드의 `requester_name`으로 미리 채워짐).
- `app/templates/request_detail.html`: 배정담당자/총괄관리자에게 같은 바로가기 추가.
  **부수 발견·수정**: 같은 파일의 "목록으로" 링크가 배정담당자에게도 무조건 `/requests`로
  걸려 있었는데, 배정담당자는 애초에 그 라우트 접근 권한이 없어 자기 홈(`/dispatch`)으로
  다시 튕겨나가는 문제를 발견 — 역할별로 링크가 갈라지도록 수정.

## 원인
사용자 질문 "배정담당자의 /requests 접근 제한이 뭐야?"에 답한 뒤, "해당 청구인의 과거
이력에 대해서만 검색가능하게 하고 싶어"로 구체적인 요구사항을 받음 — 전체 접근을 여는 게
아니라 딱 필요한 만큼만 좁혀서 여는 방향으로 설계.

## 검증
- 확인 방법: **주의** — 이번에도 한글 쿼리 파라미터를 다루므로 curl 대신 처음부터 Python
  `requests`로 테스트. (1) 빈 검색어는 폼만 보이고 결과 테이블 없음, (2) 샘플 데이터의
  실제 청구인 이름("김도윤")으로 검색 시 해당 건이 조회됨, (3) 존재하지 않는 이름은
  "과거 청구가 없습니다" 안내, (4) 업무담당자는 403 대신 자기 홈으로 303 리다이렉트,
  (5) 총괄관리자는 정상 접근, (6) 부분 일치("김"만 입력)나 원문 텍스트를 이름 자리에
  넣었을 때 둘 다 결과가 나오지 않음(정확 일치만 허용됨을 확인), (7) 배정담당자로
  청구 상세를 열었을 때 "목록으로" 링크가 `/dispatch`를 가리키는지 확인. Playwright로
  화면과 사이드바 활성 링크까지 스크린샷 확인.
- 결과: 전부 기대대로 동작. `python -m compileall app` 통과.

## 리스크
- 영향 범위: 새 라우트 1개 + 기존 화면에 링크 추가뿐, 기존 `/requests`·`/dispatch` 접근
  제어는 변경하지 않음.
- 주의사항: 이름 완전 일치만 지원하므로, 같은 사람이 이름을 다르게 표기해 접수했다면
  (오탈자 등) 찾지 못할 수 있음 — 의도된 트레이드오프(부분검색을 허용하면 다른 사람과
  이름이 비슷한 청구인의 정보까지 노출될 여지가 커짐).
