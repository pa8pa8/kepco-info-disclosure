## 변경 요약
판단 완료 후 화면 텍스트로만 남아있던 통지서를 실제 발송 가능한 문서 형태로 볼 수 있는
인쇄용 화면(`/requests/{id}/notice`) 신규 구현. 역할별 재점검 "통지서 산출물 없음" 해결.

## 변경 내용
- `app/main.py`: `GET /requests/{request_id}/notice` 신규 — `request_detail`과 동일한
  권한 체크(총괄관리자/배정담당자/업무담당자, 업무담당자는 본인 배정건만) 후 미확정
  건이면 상세 페이지로 리다이렉트. 확정된 건만 `notice_print.html`을 렌더링.
- `app/templates/notice_print.html` 신규 — `base.html`을 상속하지 않는 독립 문서
  템플릿(사이드바 등 앱 UI 없이 실제 공문서처럼 보이도록). 문서번호, 수신인, 통지일,
  접수 내역 표, 처리 결과(통지 유형 + 통지문 전체), 처리 담당자, 법적 근거 안내문 포함.
  `@media print` 규칙으로 인쇄 시 툴바("인쇄/PDF로 저장" 버튼, "청구 상세로" 링크)와
  카드 그림자/여백을 제거해 실제 인쇄물이 깔끔하게 나오도록 함.
- `app/templates/request_detail.html`: "최종 통지" 카드에 "📄 통지서 보기 / 인쇄" 링크
  추가(새 탭에서 열림).
- 별도 라이브러리(docx/pdf 생성) 없이 브라우저 내장 인쇄 기능만으로 PDF 산출물을 만들 수
  있게 구현 — `docs/DEVELOPMENT_STANDARD.md`의 "외부 패키지 최소화" 원칙 준수.

## 원인
사용자 지시 "이어서 진행해줘" — 역할별 재점검에서 "이 시스템의 존재 이유와 직결"로 꼽았던
3대 항목(재배정/처리기한/통지서 산출물) 중 마지막 항목.

## 검증
- 확인 방법: 격리 환경(포트 8092, 별도 DB)에서 (1) 미확정 상태에서 `/notice` 접근 시
  303으로 상세 페이지로 리다이렉트되는지, (2) 청구를 배정→위저드 전체 진행해 "공개"로
  확정한 뒤 (3) 배정된 staff1은 200, 배정 안 된 staff2는 303, dispatcher/manager는
  둘 다 200으로 볼 수 있는지, (4) 렌더링된 HTML에 문서번호·제목·통지 유형·법률 근거
  문구가 전부 포함되는지 grep으로 확인. Playwright로 일반 화면과 `emulate_media('print')`
  인쇄 미리보기 둘 다 스크린샷 확인 — 인쇄 모드에서 툴바가 정확히 사라지고 카드 여백/
  그림자 없이 깔끔한 문서 형태로 나오는 것 확인.
- 결과: 전부 기대대로 동작. `python -m compileall app` 통과.

## 리스크
- 영향 범위: 새 라우트 + 새 템플릿 1개, 기존 화면에는 링크 하나만 추가 — 회귀 없음.
- 주의사항: 실제 우편/이메일 발송 기능은 아니며, 사람이 "인쇄 → PDF 저장 → 별도 발송"
  하는 수동 단계가 남아있음(이 시스템의 범위를 "판단 지원"으로 한정한 기존 설계와 일관).
