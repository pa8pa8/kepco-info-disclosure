## 변경 내용

### 1. 대시보드 저장형 XSS 수정 (심각도: 높음)
- `app/static/js/app.js`의 `renderPendingList`/`renderRecentList`(대시보드 폴링
  렌더러)가 `requester_name`/`request_target`을 이스케이프 없이 템플릿 리터럴로
  `.innerHTML`에 꽂고 있었음. 이 두 필드는 청구인이 감시 폴더로 제출하는 실제 원문
  (`request_target`은 AI가 원문에서 문장 하나를 그대로 추출한 것)이라, 악의적으로
  `<img src=x onerror=...>` 같은 내용을 포함한 청구 하나만 접수돼도 총괄관리자가
  대시보드를 여는 순간 임의 스크립트가 실행될 수 있었다. Jinja2 서버 렌더링 화면은
  자동 이스케이프로 이미 안전했지만, 이 두 함수는 클라이언트 JS가 직접 그리는
  경로라 별개였다.
- `renderRecommendations`(AI 예시 추천 카드)의 담당자 이름·추천 사유도 같은 패턴으로
  이스케이프 추가(예시 파일은 운영자가 관리하는 파일이라 위험도는 낮지만 일관성 차원).
- 검증: 실제로 `<img src=x onerror=window.__xss_fired=true>`를 `requester_name`에,
  `<script>window.__xss_fired2=true</script>`를 `request_target`에 넣어 청구를
  시딩하고 개발 서버에서 총괄관리자로 대시보드를 열어 Playwright로 확인 — 수정 전
  코드였다면 `window.__xss_fired`가 `true`가 됐을 상황에서 `false`(스크립트 미실행)
  이고, 화면에는 `&lt;img src=x ...&gt;`처럼 리터럴 텍스트로만 표시됨을 확인.

### 2. 감시 폴더 재스캔 중복 접수 버그 수정 (심각도: 중간)
- `app/db.py`의 `get_log_source_files()`가 `ORDER BY` 없이 `LIMIT 500`을 걸고
  있었다. `RequestProcessorService.scan_once()`가 이 결과를 "이미 접수된 파일" 집합으로
  써서 신규 파일만 골라내는데, 누적 청구가 500건을 넘으면 정렬 순서가 정해지지 않은
  500개짜리 부분집합만 돌아와 오래된 접수 파일 일부가 "모르는 파일" 취급돼 재스캔
  시 중복으로 다시 접수될 수 있었다. `LIMIT` 없이 전체를 가져오도록 수정 — 파일명
  문자열 하나만 담는 단일 컬럼 조회라 수만 건이 쌓여도 가벼움.
- `tests/test_db.py` 신규: 520건을 시딩해 예전 쿼리라면 마지막에 넣은 파일이
  빠지는 걸 직접 재현해 회귀 테스트로 고정(수정 전 쿼리로 되돌리면 이 테스트가
  실패하는 것도 확인).

  Playwright로 스크립트 미실행·이스케이프 렌더링 확인 후 테스트 데이터 정리.

## 리스크
- 영향 범위: `app/static/js/app.js`(대시보드 렌더링 함수 3개), `app/db.py`
  (`get_log_source_files` 하나). 백엔드 판단·권한·배정 로직은 건드리지 않음.
- 주의사항: 앞으로 `.innerHTML`에 API 응답 필드를 직접 넣는 새 렌더링 함수를 추가할
  때는, 그 필드가 청구인/사용자 입력에서 유래했는지 먼저 확인하고 `escapeHtml()`을
  기본값으로 쓸 것 — 이번 버그가 "안전한 게 기본"이 아니라 "따로 안 감싸면 위험"한
  구조였다는 방증.
